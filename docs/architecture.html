Purpose & scope

What this document is for

The engineering reference for this service — read it before changing how a request is authenticated, scraped, stored, or billed.

The service sells subscription access to structured product-detail-page (PDP) data, starting with Shopee Brazil. Everything below is written to answer one question the code alone doesn't: why does it work this way, and what happens if a piece is removed. For step-by-step operating instructions (provisioning clients, reading the dashboard), see the Operator Manual.

The five moving parts

One FastAPI process holds four of them; Supabase is the only external dependency besides the target website itself.

03 — Request lifecycle

What happens between the call and the response

Six gates, in order — any one of them can end the request before it reaches the target site.

Why a fresh context, not a retry in place

A context that just got shown a CAPTCHA carries the cookies and fingerprint that triggered it. Reusing it would likely reproduce the same block; a new context (optionally through a different proxy) gives the retry an honest chance instead of guaranteeing a repeat failure.

05 — Multi-site extensibility

Why adding a website doesn't touch the core

Auth, rate limiting, storage, and the dashboard are written against a site_key string and a normalized data shape — neither knows Shopee exists.

The three steps

  1. Insert a row into sites (site_key, display_name, base_domain).
  2. Write app/scrapers/sites/<site>.py implementing BaseScraper.fetch_pdp — return the common fields, put anything site-specific in raw.
  3. Add one line to SCRAPER_REGISTRY in app/scrapers/registry.py.

The new site is immediately callable at POST /v1/<site_key>/pdp, billed and rate-limited by the same plans, and shows up in the same dashboard.

06 — Rate limiting & quota

Two layers, two different lifetimes

LayerEnforced againstStorageSurvives a restart?
Burst limitrequests_per_minuteIn-memory sliding window, per keyNo — resets on restart
Quotadaily_quota / monthly_quotausage_logs row countYes

The burst limiter trades durability for zero DB round-trips on the hot path — losing a few seconds of window on restart is cheap; a DB read on every single request to enforce a per-minute cap would not be. Quota, which only needs checking once per request and must be correct across restarts and (eventually) multiple app instances, reads the same usage_logs table the dashboard does.

Scaling to multiple instances

The burst limiter is a single process's in-memory dict — correct for one instance, wrong for three behind a load balancer (each would enforce its own window). Swap it for Redis INCR+EXPIRE behind the same check_burst_limit call site; nothing else changes.

07 — CAPTCHA policy

Detect and back off, never defeat

The service deliberately stops at recognizing a CAPTCHA/anti-bot wall — matching known page signatures and URL patterns — and retrying with a clean browser context. It does not attempt to solve challenges. CaptchaSolver in app/scrapers/captcha.py is a no-op hook left in place if a third-party solving service is ever wired in deliberately; that's a decision to make explicitly, not a default behavior.

After CAPTCHA_MAX_RETRIES fresh-context attempts, the request fails as captcha_blocked (HTTP 502) rather than looping indefinitely.

08 — Security notes

What's protected, and how

  • API keys are never stored raw — only a SHA-256 hash. create-key prints the secret once; losing it means issuing a new one.
  • The Supabase service-role key bypasses row-level security — it's a server-side secret, never sent to a client and never referenced from the dashboard's browser-side JavaScript.
  • The admin dashboard is a separate trust boundary from a client's own key — HTTP Basic auth on /dashboard versus key-scoped access on /dashboard/me, so a leaked client key exposes only that one client's usage.
  • Expiry is checked on every request, not by a background job — there's no window where a lapsed key still works because a cron hasn't run yet.
