01 — Overview

What this service does

One sentence: clients pay for a subscription, get an API key, and call your API to get clean, structured product data instead of running their own scraper.

A client sends a Shopee Brazil product URL with their API key; the service returns the product's title, price, rating, images, and other detail-page fields as JSON. Behind that one call, the service handles browser automation, anti-bot walls, rate limiting, and logging every request so both you and the client can see exactly how much they've used.

This manual covers day-to-day operation. For how it's built internally — components, data flow, schema — see the companion Architecture & Working Document.

02 — Setup

Get the service running

One-time steps, in order, from a clean checkout.

1. Install dependencies

# from the shopee_scraper_api/ directory
python -m venv .venv
.venv\Scripts\activate          # macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
playwright install chromium

2. Create a Supabase project

In the Supabase SQL editor, run app/db/schema.sql once. It creates six tables (clients, plans, api_keys, sites, usage_logs, pdp_data) and seeds a shopee_br row into sites.

3. Configure environment

cp .env.example .env
VariableMeaning
SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEYFrom your Supabase project's API settings. The service role key bypasses row-level security — keep it server-side only.
ADMIN_DASHBOARD_PASSWORDGate for the all-clients dashboard at /dashboard.
MAX_CONCURRENT_SCRAPESHow many browser contexts run at once. Raise cautiously — each one is a real Chromium instance.
CAPTCHA_MAX_RETRIESFresh-context retries before a request gives up as captcha_blocked.
PROXY_LISTJSON array of proxy URLs, rotated round-robin. Leave as [] to scrape without one.

4. Start the server

uvicorn app.main:app --reload

Visit http://localhost:8000/health — a {"status": "ok"} response means the service and its Playwright browser started cleanly.

03 — Provisioning a client

Sell a subscription

There's no billing integration yet — you run three CLI commands per client, from shopee_scraper_api/.

Do this once per pricing tier

A plan defines the ceiling a subscription buys: burst rate, daily/monthly quota, and how many days it lasts before it needs renewing.

python scripts/manage_keys.py create-plan \
  --name starter --rpm 30 \
  --daily-quota 1000 --monthly-quota 20000 \
  --duration-days 30

Then, per client:

python scripts/manage_keys.py create-client \
  --name "Acme Corp" --email acme@example.com

python scripts/manage_keys.py create-key \
  --client-email acme@example.com --plan-name starter
The key prints once

Only its hash is stored in Supabase — if you lose it, issue a new one with create-key again. There's no "reveal key" command by design.

Send the client the printed sk_... value and the base URL of your deployment. That's everything they need to start calling the API.

04 — Calling the API

The one endpoint clients use

Every supported website is called the same way — only the site_key in the path changes.

POST/v1/shopee_br/pdp

Header: X-API-Key: sk_... · Body: {"url": "<product page URL>"}

curl -X POST https://your-domain/v1/shopee_br/pdp \
  -H "X-API-Key: sk_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://shopee.com.br/produto-i.123.456"}'

A successful call takes a few seconds — the request drives a real headless browser to the page, so it's not instant like a cached lookup. If the service is under load, it queues rather than piling on more concurrent browsers than MAX_CONCURRENT_SCRAPES allows.

05 — Reading the response

Response shape

Every site adapter normalizes into the same envelope, so switching sites later doesn't change how a client parses a response.

{
  "status": "success",
  "data": {
    "site_key": "shopee_br",
    "product_url": "https://shopee.com.br/produto-i.123.456",
    "external_product_id": "123.456",
    "title": "Wireless Earbuds Pro",
    "price": 129.90,
    "currency": "BRL",
    "rating": 4.8,
    "sold_count": 1200,
    "image_urls": ["https://cf.shopee.com.br/file/..."],
    "raw": { "…site-specific fields live here…": true }
  }
}

The top-level fields (title, price, rating, …) are guaranteed across every website this service supports. raw carries whatever extra fields that particular site exposes — treat it as a bonus, not a contract.

07 — Using the dashboard

Seeing how much data is being pulled

Two views of the same data, scoped differently.

Admin view — every client

GET /dashboard, gated behind HTTP Basic auth (ADMIN_DASHBOARD_PASSWORD). Shows requests per day, per month, a custom date range, and a breakdown by outcome (success / failed / CAPTCHA-blocked / rate-limited / quota-exceeded) across all clients.

Client self-service view

GET /dashboard/me?api_key=sk_... — no admin password needed, scoped to that one key. Send clients this link (with their own key) if you want them checking their own usage without asking you.

  • Preset ranges (7/30/90 days) plus a custom start/end date picker
  • A daily line chart with a plain table fallback for accessibility
  • A monthly bar chart, 12 months back
  • Today's count and this month's count as headline numbers, independent of whatever range is selected
08 — Renewing & revoking

Keeping access in line with payment

The API checks expires_at on every request — there's no cron job to run, but there's also no billing webhook yet, so these are manual calls.

SituationCommand
Client renewspython scripts/manage_keys.py extend-key --key-prefix sk_AbCdEfGh --days 30
Client stops paying / abuses the servicepython scripts/manage_keys.py revoke-key --key-prefix sk_AbCdEfGh
Check who's activepython scripts/manage_keys.py list-keys

key-prefix is the first 11 characters of a key (e.g. sk_AbCdEfGh) — printed by create-key and shown in list-keys, so you never need the full secret to manage a client.

Once expires_at passes, the very next API call from that key gets a 403 and the key's status flips to expired automatically — no separate deactivation step.

09 — Adding a website

This isn't Shopee-only by design

Every part of this manual — API keys, rate limits, the dashboard — works identically for any site the service supports; only the site_key in the URL changes. Turning on a second website is a developer task (three steps, no schema change) covered in the Architecture & Working Document, §6.

10 — Troubleshooting

Common issues

Every request times out around 30 seconds

That's SCRAPE_TIMEOUT_SECONDS — Shopee's page didn't finish loading, or its internal PDP API response never arrived. Check the product URL loads in a normal browser first.

Lots of captcha_blocked results

Shopee is rate-limiting your scraping IP, not a client's API key. Slow down request volume, and consider setting PROXY_LIST so requests don't all originate from one IP.

A client says the dashboard shows zero requests

Confirm they're using the full API key in the ?api_key= link — the dashboard resolves it by hash, so a partial or mistyped key silently matches nothing rather than erroring.

New Playwright/Chromium errors after an OS or dependency update

Re-run playwright install chromium — the bundled browser binary is pinned to the installed Playwright version.
