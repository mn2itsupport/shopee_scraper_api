01 — Debugger setup

Get a breakpoint to actually stop

The app is one FastAPI process with an async lifespan (the browser pool) and mixed sync/async code, so how you launch it matters.

.vscode/launch.json in this repo runs uvicorn directly under the debugger, without --reload:

{
  "name": "Debug FastAPI (uvicorn, no reload)",
  "type": "debugpy",
  "request": "launch",
  "module": "uvicorn",
  "args": ["app.main:app", "--port", "8000"],
  "jinja": true,
  "justMyCode": true,
  "cwd": "${workspaceFolder}",
  "console": "integratedTerminal"
}
Why not --reload

--reload runs your app in a child process supervised by uvicorn's reloader. Breakpoints set in the parent debugger session never fire in that child. This is the same reason app/main.py:10-14 has to explicitly force WindowsProactorEventLoopPolicy on Windows — the reloader's default loop can't spawn the Chromium subprocess Playwright needs.

  1. Install the VS Code Python extension (ships debugpy automatically — no requirements.txt change needed).
  2. Confirm .env is filled in (Supabase URL/key at minimum) and app/db/schema.sql has been applied — auth and quota checks hit real tables.
  3. Run Debug > Start Debugging (F5) with "Debug FastAPI (uvicorn, no reload)" selected.
  4. Server comes up on :8000 inside the debugger. Set breakpoints (click left of the line number, or F9) in any file below — they'll bind live, no restart needed for files not yet executed.
02 — Pipeline map

Every stage a request passes through

Same six gates as the architecture doc's lifecycle diagram, but with exact line numbers so you can drop a breakpoint straight in.

Async offload

Every DB call on this path (get_site_id, check_quota, log_usage, _insert_pdp_data, the auth lookup) is wrapped in asyncio.to_thread because the Supabase client is synchronous. Stepping (F11) into one of these still lands you in the right function — the debugger follows the worker thread — but the Call Stack panel will show the thread-pool machinery above your frame instead of a plain call chain.

03 — CAPTCHA retry trace

What actually happens inside scrape_with_retries

app/scrapers/registry.py:24-49. Set a breakpoint on line 32 (the for attempt in ... line) and watch attempt and last_error across iterations.

1

Loop bound. range(settings.captcha_max_retries + 1). Default CAPTCHA_MAX_RETRIES=2 → 3 total tries (1 initial + 2 retries).

2

Jitter, every attempt. Line 33-35: a random pre_scrape_jitter_ms_min..max (default 150-500ms) sleep before each try, including the first — anti-lockstep across concurrent requests, not just retries.

3

Fresh context per attempt. Line 38: async with acquire_context() — browser_pool.py:66-87 pulls a new proxy from get_proxy_provider().next_proxy() and a new random UA. A retry is a completely different fingerprint/exit IP, not a reload of the same page.

4

Two CAPTCHA checkpoints inside the adapter. shopee_br.py:44 right after page.goto, and shopee_br.py:52 after waiting (up to scrape_timeout_seconds, polling every 0.5s) for Shopee's own PDP XHR to be captured.

5

Detection. captcha.py:29 is_captcha_page — URL contains /verify or /challenge, or the page text matches a known signature (e.g. "verifique que você é humano"). If matched, get_captcha_solver().solve(page) is tried; in BROWSER_MODE=local that's NoOpCaptchaSolver, always False — this app deliberately fails closed rather than trying to defeat a challenge.

6

Raise, then cleanup still runs. CaptchaBlockedError propagates out of the async with block. ManagedContext.__aexit__ (browser_pool.py:92-95) still closes the context and releases the concurrency semaphore — a blocked attempt doesn't leak a slot.

7

Backoff and loop. Line 40-44: last_error = exc, then 2*(attempt+1) + random(0, 1.5) seconds of sleep before the next iteration gets its own jitter + fresh context.

8

Non-CAPTCHA failures don't retry. Line 45-46: a plain ScraperError (bad JSON, missing item data) is re-raised immediately — retries only make sense against a transient anti-bot wall, not a structural parsing failure.

9

Exhausted. After the final attempt still fails, the loop ends and raise last_error (line 49) sends the last CaptchaBlockedError up to scrape.py, which maps it to status="captcha_blocked" and HTTP 502.

Forcing this path while debugging

Real Shopee CAPTCHAs are intermittent, which makes this branch hard to hit on demand. Easiest way to force it: set a breakpoint at captcha.py:29 (entry of is_captcha_page), and in the debugger's Debug Console, once paused, run return True equivalent by editing the return — or simpler, temporarily add return True as the first line of is_captcha_page and step through a whole retry cycle, then remove it. Don't leave that change in.

04 — Guided debug session

One request, start to finish

With the debugger running (section 01) and breakpoints set at scrape.py:37, auth.py:27, rate_limiter.py:24/37, registry.py:32, and shopee_br.py:31:

  1. From a second terminal, fire a request: 
    curl -X POST http://localhost:8000/v1/shopee_br/pdp `
  -H "X-API-Key: sk_..." -H "Content-Type: application/json" `
  -d '{"url": "https://shopee.com.br/product-slug-i.123.456"}'
  2. Execution pauses at scrape.py:37. Inspect key in the Variables pane — note it's already an AuthedKey, because require_api_key ran as a FastAPI dependency before the handler body. F5 to continue, or F11 earlier if you'd set a breakpoint inside auth.py to catch it first.
  3. At rate_limiter.py:24, hover window — it's a deque of monotonic timestamps for this one API key. F10 through the popleft loop to watch stale entries drop off.
  4. At registry.py:32, F11 into acquire_context() to watch which proxy/UA got picked for this attempt, then Shift+F11 back out and F11 again into fetch_pdp.
  5. Inside fetch_pdp, set a breakpoint at line 54 (if "response" in captured) to see whether Shopee's XHR was actually captured, or whether the request is about to fall through to _parse_dom_fallback.
  6. F5 to run to completion. Back in scrape.py, the finally block (line 66-68) always executes next — check status and elapsed_ms here regardless of which path you took.
  7. Inspect the final ScrapeResponse or HTTPException right before it returns to see exactly what the client receives.

Debug Console is not just for reading

While paused, the Debug Console evaluates arbitrary expressions in the current scope — useful for probing without adding a new breakpoint: key.daily_quota, pdp.raw.keys(), len(window), or even calling a side-effect-free method on a paused object.

05 — Terminal / pdb alternative

No VS Code? Use the standard library

Drop breakpoint() on any line — e.g. inside fetch_pdp in shopee_br.py — then run uvicorn normally, without --reload:

uvicorn app.main:app

The request thread drops into pdb at that line. Core commands:

CommandEffect
nnext line, don't descend into calls
sstep into the call on this line
ccontinue to next breakpoint
p <expr>print an expression in current scope
llist source around the current line
wprint the call stack (where)
06 — Repo-specific pitfalls

Things that look like debugger bugs but aren't

  • Breakpoint silently never fires with --reload — reloader runs your app in a child process the parent debugger isn't attached to. Use the provided launch config (no reload) instead.
  • The scrape "hangs" with no breakpoint hit — check MAX_CONCURRENT_SCRAPES (default 3). If that many contexts are already open (including ones you're paused inside of in another debug session), a new request blocks on the semaphore in browser_pool.py:68 until one releases. Pausing at a breakpoint mid-scrape holds that slot the whole time you're paused.
  • You can't see the browser — headless is on by default. Set PLAYWRIGHT_HEADLESS=false in .env to watch Chromium visually while stepping through shopee_br.py.
  • Stepping into Supabase/Playwright internals is noisy — justMyCode: true in launch.json keeps F11 from descending into library code. Flip to false only if you specifically need to see inside them.
  • to_thread calls show extra frames — any DB call (see the callout in section 02) runs on a worker thread; the Call Stack panel will show thread-pool frames above your code, not a clean async chain.
  • Rate limiter state resets on every debugger restart — check_burst_limit's window is an in-memory dict (rate_limiter.py:20), scoped to the process. Restarting the debug session clears it.
